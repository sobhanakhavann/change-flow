# Research: ChangeFlow Technical Decisions

## Current local startup configuration — 2026-11-16

The owner simplified local startup: no environment file or variables are required. The default database is `${user.dir}/changeflow.sqlite`, inside the application working directory, and logs use the console. Existing parent-directory validation still applies to an explicitly overridden path. Spring process environment variables may override the defaults; `.env` is not automatically imported. Earlier instructions requiring external storage or copying `.env` are superseded for local startup. Authentication, migrations and business rules are unchanged.

Updated 2026-11-15 after Tasks generation. Owner-approved change: replace PostgreSQL with persistent file-based SQLite. Product source: [spec.md](spec.md), unchanged. ## Runtime and dependencies

**Decision**: Keep Java 21, Spring Boot 4.1.2, dependency-management 1.1.7 and Gradle Wrapper 9.8.2. Retain Spring MVC, Security, JDBC and Boot test starters. Select org.xerial:sqlite-jdbc 3.53.4.0, managed by the Boot 4.1.2 BOM; retain spring-boot-starter-flyway 4.1.2 and its managed flyway-core 12.4.0. Remove the planned PostgreSQL driver/database module and Testcontainers dependencies; tests use the actual SQLite JDBC engine and temporary files, not Docker.

**Rationale**: One embedded engine and no database server/container simplify execution. [Boot coordinates](https://docs.spring.io/spring-boot/appendix/dependency-versions/coordinates.html) explicitly manage sqlite-jdbc 3.53.4.0. [Pinned Xerial POM](https://raw.githubusercontent.com/xerial/sqlite-jdbc/3.53.4.0/pom.xml) targets Java 8 bytecode, with Java 9 multi-release classes, making the Java 21 runtime a compatible JVM target. Its build-time JUnit dependencies are not application runtime requirements. [Xerial driver](https://github.com/xerial/sqlite-jdbc) packages native libraries for major desktop/server platforms; native loading on the actual target remains an implementation check. The driver bundles SQLite 3.53.4; record SELECT sqlite_version() and JDBC metadata during validation.

**Alternatives**: A newer driver override adds an unnecessary deviation from the BOM; JPA adds ORM behavior without a need; R2DBC changes the approved JDBC architecture; H2 and SQLite :memory: do not prove persistence or real shared-file locking.

Existing stack compatibility remains supported by [Boot requirements](https://docs.spring.io/spring-boot/system-requirements.html) and [Gradle 9.8.2 release](https://docs.gradle.org/9.8.2/release-notes.html). Managed Security 7.1.2 and JUnit 6.0.3 remain selected; starter-security-test and starter-webmvc-test retain Boot 4 test integration. Actual binary resolution/build has not been verified in this session. Earlier observations: local java -version reported 25.0.4; Wrapper startup failed creating C:\.gradle lock parent. Those are historical evidence, not new successful checks.

## Migration compatibility (verified, not assumed)

**Decision**: Retain Flyway via Boot's Flyway starter and core only; no flyway-database-postgresql or speculative flyway-database-sqlite artifact.

**Rationale**: [Redgate SQLite documentation](https://documentation.red-gate.com/flyway/reference/database-driver-reference/sqlite) identifies org.sqlite.JDBC, SQLite URL handling and SQL migration support, but documents limited historically verified versions rather than certifying our exact engine. For the exact managed version, [Flyway 12.4.0 SQLiteDatabaseType](https://raw.githubusercontent.com/flyway/flyway/flyway-12.4.0/flyway-core/src/main/java/org/flywaydb/core/internal/database/sqlite/SQLiteDatabaseType.java) and [core plugin registry](https://raw.githubusercontent.com/flyway/flyway/flyway-12.4.0/flyway-core/src/main/resources/META-INF/services/org.flywaydb.core.extensibility.Plugin) confirm the implementation is in core. [Boot initialization](https://docs.spring.io/spring-boot/how-to/data-initialization.html) establishes starter wiring.

Flyway's SQLite limitations matter: no concurrent migrators, no multiple schemas, and no nested transaction statements in migration scripts. Run exactly one migration process per file before serving traffic; fail startup on migration/validation errors. Use V1/V2/V3 SQLite STRICT SQL, with no embedded BEGIN/COMMIT, PostgreSQL casts or schema-qualified names. Set connection PRAGMAs outside migration transactions. Do not enable clean or automatic baseline/repair. Existing deployed databases, if any, must not be rewritten or deleted; importing legacy data needs a separate explicitly approved migration procedure.

**Alternatives**: A homegrown migration ledger duplicates Flyway; Liquibase adds a tool change without evidence of incompatibility. Exact Flyway+driver+engine startup, repeat startup/checksum validation, transaction behavior and schema tests remain a required execution gate, not a claimed certified test pass. If this gate fails, report the concrete failure before selecting another migration mechanism.

## Persistent file and connection setup

**Decision**: A single local persistent SQLite file, absolute path configured by CHANGEFLOW_DB_PATH; no :memory:, shared-cache URI, remote filesystem or classpath/build-directory production data. Default documented location is outside the repository under the local application-data directory. Directory and file permissions restrict access to the service/operator. SQLite has no datasource username/password authentication; retain application-level Basic users and BCrypt hashes in app_user.

Use a repository-layer DataSourceConfiguration with Xerial SQLiteDataSource (independent short-lived physical connections; no pool/single shared connection). Driver properties configure DEFERRED transactions, foreign_keys=ON, read_uncommitted=OFF, busy_timeout=5000 milliseconds and synchronous=FULL on each connection. Establish journal_mode=WAL once on exclusive startup before Flyway, verify its returned mode, and verify critical per-connection PRAGMAs rather than assuming they applied. Path and busy timeout (CHANGEFLOW_SQLITE_BUSY_TIMEOUT_MS) are external settings; invalid settings fail startup. This is a bounded lock-wait default, not a performance objective.

**Rationale**: [SQLite PRAGMAs](https://sqlite.org/pragma.html) and [Xerial configuration](https://raw.githubusercontent.com/xerial/sqlite-jdbc/3.53.4.0/src/main/java/org/sqlite/SQLiteConfig.java) expose these controls. WAL permits readers alongside the single writer and requires all users on the same host/local filesystem. The file, -wal and -shm form the live database state; never remove sidecars to clear locks. [WAL documentation](https://sqlite.org/wal.html) describes these constraints. No attached databases in business transactions. Keep transactions short and close cursors/connections; preserve default automatic checkpoints and monitor checkpoint failures without deleting state.

**Alternatives**: A singleton connection hides contention and serializes reads; a pool adds lifecycle/PRAGMA complexity without an established requirement; network-file deployment violates WAL assumptions. No extra application lock or writer queue needed.

Implementation task T003 must add Git exclusions for /var/changeflow/, *.db, *.db-wal, *.db-shm, *.db-journal, *.sqlite and equivalent -wal/-shm/-journal, and *.sqlite3 and their sidecars. Operator-chosen other filenames must remain outside the checkout or be explicitly excluded. This revision does not edit .gitignore or create a file. Never remove existing tracked data automatically.

## Transactions, authorization and concurrency

**Decision**: Spring JDBC transaction manager with driver DEFERRED transactions, default SQLite SERIALIZABLE snapshot semantics, no shared cache/dirty reads. Do not request JDBC READ_COMMITTED (SQLite does not implement the former PostgreSQL behavior). Do not set JDBC readOnly/enforceReadOnly for read services: Flyway/Xerial SQLite read-only transaction support differs; read services simply issue no writes.

The first database SELECT inside each new operation transaction reads current enabled status/roles in one statement; it also establishes that operation's snapshot. No earlier resource query may pin an older snapshot. Authentication uses an independent completed lookup, never a reused long transaction. Revocation committed before this first SELECT is visible; already authorized operations are not reauthorized in their snapshot, but still may fail integrity/locking checks. Future operations always start a new snapshot.

CAS matches id plus the caller's original version. Content changes and reason inserts commit together. SQLite serializes writers even for different request rows. WAL readers can share an old snapshot, but a read-to-write upgrade after a rival commit may raise SQLITE_BUSY_SNAPSHOT rather than return zero CAS rows. Do not treat busy_timeout as a guaranteed wait on snapshot upgrade; it can fail immediately. [Isolation](https://sqlite.org/isolation.html), [transactions](https://sqlite.org/lang_transaction.html), and [result codes](https://sqlite.org/rescode.html) establish these behaviors.

**Failure classification**:
1. Known stale If-Match or zero-row CAS: rollback; fresh visibility/version read outside the old transaction. Hidden/missing → existing generic 404; readable stale → existing 412.
2. SQLITE_BUSY_SNAPSHOT: rollback the entire operation, close old snapshot and perform the same read-only diagnosis with a fresh enabled/current-role snapshot. Readable version changed → 412; missing/hidden → 404; unchanged request version (e.g. another resource or role was updated) → existing 503 SERVICE_UNAVAILABLE, not a false version conflict.
3. Other SQLITE_BUSY after bounded wait, or SQLITE_LOCKED: no replay; rollback/discard connection, 503. Never classify a lock as successful business mutation. Attempt privacy-safe diagnosis for resource routes when possible; if storage prevents determining visibility, return generic 503 with no request state/version. No new lock error schema or retry-success response.
4. SQLITE_FULL, IOERR, READONLY, CANTOPEN and storage failures: rollback/close as possible, 503 with sanitized detail. Unexpected failures use existing 500; never expose paths/SQL/credentials. A lost commit result is an uncertain whole-operation outcome, not proof of rollback. Do not attempt automatic COMMIT retries or business-command retries. An authorized GET can inspect the outcome later without refreshing/replaying the original command.

The driver's internal bounded busy-handler waiting is not business-command replay. No transaction restart on a new snapshot, no @Retryable, no refresh of If-Match. Diagnostic reads never execute domain actions.

**Alternatives**: BEGIN IMMEDIATE avoids snapshot upgrades but acquires the only writer slot before authorization/resource reads, blocks unrelated mutations/revocation and prevents the specified both-read-before-write fixtures. DEFERRED plus explicit failed-upgrade handling preserves simple Spring JDBC integration and deterministic contention tests. No claim of row-level parallel writers is made.

## Analyze remediation: U1 / I1 / I2 / U2

**Decision (U1)**: The service orchestrator runs outside all transaction callbacks and has no enclosing @Transactional boundary. Reject accidental ambient transactions rather than joining them. Execute each mutation exactly once through TransactionTemplate with a Spring JDBC transaction manager; authentication has already finished. A callback failure must escape execute so rollback completes and JDBC resources are unbound before the orchestrator classifies it. Do not merely catch inside the callback, mark rollback-only and diagnose there.

Only after confirmed rollback/afterCompletion(ROLLED_BACK) and callback exit, start a separate fresh DEFERRED diagnostic transaction through another TransactionTemplate execution. It is read-only by behavior (SELECT only), without JDBC readOnly/enforceReadOnly flags. Its first SELECT rereads enabled status and current roles; then load resource and enforce current read access. Do not carry the failed operation's permission grant into diagnosis. Missing or currently inaccessible (including disabled/no-longer-entitled caller) returns the same generic 404 without state/version details. If accessible, compare current resource version against the immutable ORIGINAL caller If-Match: mismatch gives 412, unchanged version after snapshot failure gives sanitized 503. Diagnostic roles/access reads share the new snapshot. No domain action, CAS, reason insert, If-Match refresh or business replay occurs in diagnosis.

A normal already-authorized operation may still finish under its original permission snapshot; this does not grant a separate diagnostic read access after rollback. If rollback cannot be confirmed or commit acknowledgement is uncertain, do not enter stale-conflict diagnosis or assert rollback: close/discard as possible, return safe 503 and leave outcome uncertain. Successful commit returns only after execute completes.

**Rationale**: Explicit callback completion prevents reuse of a rollback-only transaction or stale JDBC-bound snapshot. Fresh diagnostic authorization prevents exposing a request after the caller loses access. **Alternatives**: Catching within an annotated transaction or reusing the original role snapshot does not satisfy the diagnostic access boundary; restarting the command is forbidden.

**Decision (I1/I2)**: T003 authors configuration only. First actual startup/migration/WAL/schema verification is T014 after T004–T006 and T013. Foundation models/validation T007/T008 form wave A; policy/identity T009/T010 form wave B after model stabilization; T011 follows identity. **Rationale**: Runtime checks require schema scripts; separate files do not remove type dependencies. **Alternatives**: Running migrations in setup or declaring all foundation tasks independent creates false completion/dependency claims.

**Decision (U2)**: Split lock tests into two distinct paths. Snapshot/DEFERRED-upgrade tests deliberately establish a read snapshot and allow a competing commit before upgrade; immediate BUSY/BUSY_SNAPSHOT is acceptable and no minimum elapsed wait is asserted. For busy-timeout validation use a separate low-level JDBC connection that has NOT established a read snapshot and explicitly attempts BEGIN IMMEDIATE while another independent connection holds the writer slot on the same WAL file. This is a storage test only, not a change to production DEFERRED transaction mode. Set a short positive busy_timeout (for example 100 ms), verify its value, and use barriers/latches plus statement-entry/completion events to keep the holder locked until the blocked attempt returns. Measure the native call with a monotonic clock; require actual bounded waiting consistent with that setting (document tolerance and a generous test deadline), not just a fast BUSY result. Immediate failure does not pass timeout validation. Release holder in finally after the contender completes; no arbitrary Thread.sleep, business retries or tag refresh. Assert BUSY and safe 503 translation/no mutations separately from the eight snapshot order cases.

**Rationale**: A failed snapshot upgrade may bypass the busy handler; a writer-slot acquisition without an old read snapshot exercises bounded native waiting. **Alternative**: Treating an immediate BUSY result as timeout evidence is insufficient. These are future test requirements, not executed results.

## Model and contract details

**Decision**: SQLite STRICT tables, TEXT UUIDs in canonical lowercase form/BINARY collation, INTEGER versions and enabled 0/1 with checks, TEXT statuses/roles with checks. Use length(text) rather than char_length; application validation rejects NUL/unpaired surrogates and counts exact Unicode scalars unchanged. [STRICT tables](https://sqlite.org/stricttables.html) and [length semantics](https://sqlite.org/lang_corefunc.html) support these choices. Keep foreign_keys enabled per connection and preserve all reasons append-only.

HTTP routes, bodies, roles, ETags, version strings and error codes remain unchanged. Only storage references/503 clarification in the contract are synchronized. Persistence and Unicode limits do not change product behavior. Basic over TLS/current database roles/custom-header CSRF policy are retained from the original plan.

Use actual Xerial engine and JUnit temporary disk directories, independent JDBC connections to the same file per scenario, and no Docker/Testcontainers/H2/in-memory substitute. Eight controlled winner orders remain mandatory; accept SQLite's snapshot exception internally but assert the same 412/404 external stale outcomes after read-only diagnosis. Separately test held-lock timeouts, busy snapshot with unchanged request version, failed insert rollback, read-only/unwritable paths, restart persistence, connection PRAGMAs and Flyway single-migrator constraints.

## Implementation remediation decisions - 2026-11-15

**Transaction cleanup decision (T049):** retain the approved unpooled independent Xerial connections and Spring JDBC transaction lifecycle, but supply SqliteTransactionManager cleanup that unbinds and physically closes the owned connection rather than restoring autoCommit/isolation for reuse. Resolved Spring 7.0.10 and Xerial 3.53.4.0 sources showed that default cleanup's setAutoCommit(true) issues COMMIT in Xerial. A real-file regression with the production bean confirmed an aborted rollback could commit CAS without feedback. Physical close discards pending work without a second COMMIT; known abort, lost acknowledgement and unknown rollback are covered by native hooks and complete row checks.

**Alternatives:** only enabling rollbackOnCommitFailure does not protect a rollback which itself fails; restoring autoCommit on a logical pool close can commit/reset an unresolved transaction. Pooling/eviction adds an unapproved lifecycle and is unnecessary for the selected independent datasource. This manager is expressly for owned unpooled connections; any later pool choice must revisit physical eviction and safe reset. No automatic business or COMMIT retry, new pool/dependency or new product outcome was introduced.

**UTF-8 decision (T050):** bind raw byte[] in controllers, defer strict StandardCharsets.UTF_8 decoding with CodingErrorAction.REPORT until existing service visibility/action checks, then parse JSON and apply unchanged ContentRules. The old String converter irreversibly replaced invalid bytes. Rejecting every U+FFFD would incorrectly reject valid supplied text; filter-time decoding would interfere with privacy-first error ordering; relying on permissive encoding autodetection would not enforce the selected UTF-8 contract. Real raw-byte HTTP regressions failed before correction and passed after it. Exact numeric limits, normalization/blank semantics, API routes and error precedence remain unchanged.

Actual final build/test evidence is in quickstart.md and the implementation follow-up in convergence-report.md; earlier documentation-only compatibility statements above are historical, not current execution status. Real TLS/physical-media/human acceptance limits remain explicit.
